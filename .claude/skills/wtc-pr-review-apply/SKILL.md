# PR 리뷰 승인분 반영 + ADR 기록

`wtc-pr-review-reply`가 코멘트에 "수용, 확인 후 반영 예정" 답글을 달고 노션 기능 명세의 `코드리뷰 반영 사항`에 `승인 대기` 항목을 남긴 뒤, 사용자가 승인했을 때 이어서 실행한다. 레포·답글 마커·금지 사항(머지·rebase·강제 푸시 금지, what-to-cook 레포만)은 그 스킬과 CLAUDE.md를 그대로 따른다.

## 1. 승인 범위 확인
```bash
REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)   # what-to-cook가 아니면 중단
gh pr view {n} --repo "$REPO" --json title,body,headRefName,url
gh api repos/$REPO/pulls/{n}/comments --paginate \
  -q '.[] | {id, user: .user.login, path, line, in_reply_to_id, body, html_url}'
```
- 반영 대상 = 내(`gh api user -q .login`) 원 코멘트 중, `<!-- wtc-review-reply -->` 마커가 붙은 **수용/부분 수용** 답글이 있고 아직 "반영했습니다" 답글이 없는 것.
- 사용자가 "모두 승인"이면 전부, 일부만 말했으면 그것만. 범위가 애매하면 묻는다.
- 답글에 적은 "수정 방향"이 구현 기준이다. 그보다 넓히지 않는다.

## 2. PR 브랜치에서 수정
- `git checkout <headRefName>`이 "already checked out at <경로>"로 실패하면 그 worktree(대개 `.claude/worktrees/agent-*`)로 가서 작업한다. 새로 브랜치를 만들거나 다른 곳에서 체크아웃을 빼앗지 않는다.
- `git status`가 깨끗한지 보고 `git pull`. 남의 변경이 있으면 멈추고 묻는다.
- 수정 방향대로 고치고, 왜 그렇게 하는지 코드만으로 안 보이면 한 줄 주석을 남긴다.

## 3. 검증
- 백엔드: `./gradlew test` (관련 테스트 우선). 프론트: `npm run lint && npm run build`.
- 프론트에는 테스트 러너가 없다. 로직 수정이면 스크래치패드에서 일회성 확인 스크립트로 각 리뷰 시나리오를 직접 돌린다(예: `npx esbuild <파일> --bundle --format=esm --platform=neutral --define:import.meta.env.X='"..."'`로 묶고, fetch·localStorage·window를 가짜로 둔 node 스크립트에서 `assert`). 이 스크립트는 커밋하지 않고, 확인한 시나리오를 보고에 적는다.
- 실패하면 커밋하지 않고 원인과 함께 보고한다.

## 4. 커밋·푸시
- 리뷰 반영분을 커밋 하나로: `fix: <요약>` + 본문에 코멘트별 변경 한 줄씩 + 시스템이 지정한 Co-Authored-By 줄.
- `git push` (강제 푸시 금지). 커밋 SHA를 기록한다.

## 5. GitHub 답글
원 코멘트마다 `gh api repos/$REPO/pulls/{n}/comments/{id}/replies -f body=...`:
```
<!-- wtc-review-reply -->
> 🤖 이 답글은 Claude Code가 작성했습니다.

**[반영 완료]** 반영했습니다: https://github.com/<REPO>/pull/{n}/commits/<SHA>

- (이 코멘트에 대해 실제로 바뀐 동작 1~2줄)
```
답글의 `html_url`을 기록해 둔다(아티팩트에 쓴다).

## 6. 노션 기능 명세 갱신
- PR 본문 `관련 기능: F?-?`로 기능 명세 행을 찾고(`wtc-notion-sync`의 DB 위치) 본문을 fetch한다.
- `코드리뷰 반영 사항`의 해당 항목만 `상태: 승인 대기` → `상태: 반영 완료 ([<짧은 SHA>](커밋 링크))`로 `update_content` 한다. 다른 내용은 건드리지 않는다.

## 7. 노션 ADR
리뷰 반영이 **대안 중 하나를 고른 설계 결정**(오류 분류 기준, 동시성·재시도 방식, 캐시 전략 등)이면 ADR을 남긴다. 오타·스타일 같은 단순 수정뿐이면 건너뛰고 그렇게 보고한다.

1. ADR DB(`collection://41d46e7b-c04e-816e-8d4b-000b583fc9c2`)에서 같은 주제의 기존 ADR을 검색한다.
   - 있으면 새로 만들지 않고 그 페이지의 결정·트레이드오프에 변경을 덧붙인다. 결정을 뒤집었으면 새 ADR을 만들고 이전 것을 `대체됨`으로 바꿔 서로 링크한다.
2. 없으면 새로 만든다. 속성:
   - 결정(title): 결정 내용을 한 문장으로 (예: "프론트 토큰 재발급은 400·401만 세션 만료로 보고, 이미 갱신된 토큰이 있으면 재발급 없이 재시도한다")
   - PR: PR 링크 / 관련 기능: 기능 명세 페이지 URL / 날짜: 오늘
   - 상태: PR이 아직 머지 전이면 `제안`, 머지됐으면 `채택`
3. 본문은 `배경 / 고려한 대안 / 결정 / 근거 / 트레이드오프`:
   - 배경: 원래 구현과 리뷰가 지적한 문제(무엇이 언제 잘못되는지).
   - 고려한 대안: 기존 방식 / 리뷰 제안 / 검토한 다른 방법.
   - 결정: 실제 커밋한 동작. 파일·함수 이름은 코드 표기로.
   - 근거: CLAUDE.md 섹션·기능 명세 근거 + 커밋 링크.
   - 트레이드오프: 이 결정으로 남는 한계(남겨둔 엣지 케이스 포함).

## 8. 리뷰 현황 아티팩트 갱신
`wtc-pr-review-reply` 7장의 `WTC PR 리뷰 현황` 페이지를 같은 URL로 덮어쓴다. 먼저 `read`로 현재 내용을 받아 그 위에서 고친다.
- 반영한 항목은 승인 대기 박스에서 빼고, 표의 분류를 `반영 완료`, 답글 링크를 새 "반영했습니다" 답글로, 노션 칸에 명세와 ADR 링크를 둔다.
- 다른 PR 항목은 그대로 둔다. 메모에 검증 방법과 ADR 상태(머지 후 `채택`으로 바꿀 것)를 적는다.
- 사용자가 대화 중이면 푸시 알림은 보내지 않는다.
