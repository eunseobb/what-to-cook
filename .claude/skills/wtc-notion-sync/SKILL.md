# What To Cook 노션 동기화

레포와 PR이 원본이고 노션은 요약본이다. 작업 단위 기록은 PR에 맡기고, 노션에는 PR에 없는 정보만 적는다: 기능별 진행 상황, 설계 결정의 이유, 성능 수치. PR 본문을 노션에 옮겨 적지 않는다.

## 노션 위치
- 메인 페이지: What To Cook (`41d46e7bc04e80b79c85e16a8caf6d5d`)
- 기능 명세: `collection://41d46e7b-c04e-813e-8e09-000b17a14d5d`
  - 속성: 기능명(title), 기능 ID(F2-1 형식), 상태(Todo/In Progress/Done), 차수(1차~4차), 도메인(user/ingredient/recipe/community/recommendation/price/ai/global), API, PR, 완료일, 기술 결정(역방향 relation)
- 기술 결정 기록(ADR): `collection://41d46e7b-c04e-816e-8d4b-000b583fc9c2`
  - 속성: 결정(title), ADR(자동 번호), 상태(제안/채택/대체됨/폐기), 날짜, 관련 기능(relation), PR
- 성능 개선: `collection://41d46e7b-c04e-8166-a068-000b0087410f`
  - 속성: 개선 항목(title), 시나리오(①~⑤), 회차(1회차/2회차), 날짜, Before/After TPS, p95(ms), p99(ms), 에러율(%), TPS 개선율(수식, 직접 쓰지 않음), 관련 기능, 리포트 경로, PR

## 절차
1. **작업 내용 수집**
   - `gh pr view --json number,title,url,body,mergedAt`와 `git log`로 이번 작업을 파악한다.
   - PR 본문의 `관련 기능: F?-?` 항목으로 대상 기능을 찾는다. 없으면 변경된 패키지(도메인)로 추정하고, 추정했다고 보고에 적는다.
2. **기능 명세 갱신**
   - 기능 ID로 행을 찾고, 없으면 새로 만든다(본문: 요구사항 / 구현 방식 / 남은 이슈).
   - 상태(작업 시작 → In Progress, 기능 완성 → Done), PR 링크, API, 완료일을 갱신한다. 한 기능에 PR이 여러 개면 PR 속성은 최신 PR로 두고, 본문 '관련 PR' 목록에 링크를 추가한다.
   - 일부만 끝났으면 Done으로 바꾸지 않고 '남은 이슈'를 갱신한다.
3. **ADR (해당될 때만)**
   - 대안 중 하나를 고른 설계 결정(락 방식, 캐시 전략, 페이지네이션, 외부 API 장애 대응 등)이 있었으면 추가한다.
   - 본문: 배경 / 고려한 대안 / 결정 / 근거 / 트레이드오프.
   - 기존 결정을 뒤집었으면 이전 ADR 상태를 '대체됨'으로 바꾸고 서로 링크한다.
4. **성능 개선 (perf 작업이나 부하 테스트를 했을 때만)**
   - `docs/performance/`의 k6 결과에서 수치를 읽어 채운다. 수치를 추정하거나 지어내지 않는다. 결과 파일이 없으면 건너뛰고 알린다.
5. **보고**: 갱신·생성한 노션 페이지 링크와 변경 요약을 짧게 보고한다. 해당 사항이 없어 건너뛴 단계도 한 줄로 적는다.

## 규칙
- 비밀값, 내부 URL, 토큰은 노션에 쓰지 않는다.
- 속성 이름과 선택지는 위 스키마 그대로 쓴다. 새 선택지가 필요하면 먼저 묻는다.
