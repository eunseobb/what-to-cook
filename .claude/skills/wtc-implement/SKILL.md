# 기능 병렬 구현 (오케스트레이터)

메인 에이전트는 직접 기능을 구현하지 않고, 기능을 고르고 서브 에이전트를 배정·대기하는 일만 한다.

## 1. 대상 조회
- 기능 명세 DB(`collection://41d46e7b-c04e-813e-8e09-000b17a14d5d`)에서 상태가 Todo이고 PR이 비어 있는 행을 `우선순위` 오름차순으로 가져온다.
- 사용자가 차수나 기능 ID를 지정하면 그 범위만 다룬다.
- 실행 전에 대기열(기능 ID, 기능명, 선행기능, 분기 브랜치)을 사용자에게 보여주고 확인받는다.

## 2. 선행기능 판정
- `선행기능`(쉼표로 구분된 기능 ID)의 각 ID로 해당 행을 찾는다.
- 그 행에 PR 링크가 있으면 완료로 본다. `gh pr view <PR> --json headRefName`으로 브랜치 이름을 얻는다.
- 선행기능이 비어 있으면 분기 브랜치와 PR 대상은 `develop`이다.
- 선행기능이 하나면 그 브랜치에서 분기하고, PR 대상도 그 브랜치로 한다.
- 선행기능이 둘 이상이고 모두 완료됐는데 브랜치가 서로 다르면, 임의로 합치지 않고 그 기능은 건너뛴 뒤 보고한다.
- PR 링크가 없는 선행기능이 이번 실행에서 진행 중이면 그 서브 에이전트가 끝날 때까지 기다린다. 진행 중도 아니면 건너뛰고 보고한다.
- 선행기능 ID가 DB에 없으면 건너뛰고 보고한다.

## 3. 실행
- 동시에 실행하는 서브 에이전트는 최대 3개다. 각 서브 에이전트는 `isolation: worktree`로 띄운다.
- 하나가 끝나면 2단계 판정을 다시 해서, 실행할 수 있게 된 다음 기능을 빈 자리에 넣는다.
- 서브 에이전트를 시작할 때 노션 상태를 In Progress로 바꾼다.

## 4. 서브 에이전트에 줄 지시
- 기능 페이지 URL과 본문, 기능 ID, 분기 브랜치, PR 대상 브랜치
- CLAUDE.md를 따른다(브랜치 이름, 커밋 형식, 테스트, 금지 사항).
- ponytail 규칙을 따르되, 프로젝트 지침에 명시된 설계 요소(서킷 브레이커, Rate Limit, 캐싱, 비교 구현 등)는 ponytail 판단보다 우선한다.
- 순서
  1. `git fetch`
  2. `git checkout -b feature/<도메인>-<기능> origin/<분기 브랜치>`
  3. 구현과 테스트를 하고 커밋한다.
  4. push한다.
  5. `gh pr create --base <PR 대상 브랜치>`로 PR을 만든다. 본문 맨 위에 `관련 기능: <기능 ID>`와 선행 PR 링크를 적는다.
- 자기 기능 범위 밖의 코드는 고치지 않는다. 막히면 멈추고 이유를 보고한다.
- 결과로 PR URL, 브랜치 이름, 테스트 결과, 남은 이슈를 돌려준다.

## 5. 마무리
- 성공한 기능은 PR 링크를 노션에 기록하고, 나머지 갱신은 `wtc-notion-sync` 절차를 따른다.
- 실패하거나 건너뛴 기능은 상태를 Todo로 되돌리고 이유를 보고한다.
- 머지, rebase, 강제 푸시는 하지 않는다.
